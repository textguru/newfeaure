# 입력 산출물 품질 검증 요약서 (1p)

| 항목 | 내용 |
|------|------|
| 대상 | 요구사항정의서 · 화면설계서 · 화면레이아웃 · 프로그램설계서 · 테이블정의서 |

| 방법 | **간접 평가** — 입력 문서 원본 미제공. 생성 산출물(Java/SQL/JSP)과 README에 드러난 명세 흔적을 역추적해 판정 |
| 일자 | 2026-05-19 |

## 1. 문서별 충족도

| 문서 | 충족도 | 강점 | 코드생성 관점 약점 |
|------|:---:|------|------------------|
| 요구사항정의서 | ◐ 보통 | REQ-001~004 구조화, 규칙/예외 분리 | 검증기준(Acceptance)이 **기대값까지 명시 안 됨** → 테스트 `then` 미생성 원인 |
| 화면설계서 | ● 양호 | SCR/POP/CMP/MSG/API ID 체계, 화면-API-REQ 매핑 우수 | **에러/실패 응답 규격 부재**(resultCode 성공만), 입력 경계조건 모호 |
| 화면레이아웃 | ◐ 보통 | 영역·컴포넌트 식별 가능 | 상호작용/상태전이 정밀도 부족 → JSP UX 일부 **가정 기반** |
| 프로그램설계서 | ◐ 보통 | 4계층 매핑·정렬/페이징 규칙 명확 | **공통 아키텍처(예외핸들러·응답포맷·인증·로깅) 미정의** → 도메인 코드만 생성 |
| 테이블정의서 | ● 양호 | 6테이블 PK/FK/타입/코멘트 충실 | **공통코드 도메인 미정의**(JOB_SE_CD 등 → SQL CASE 하드코딩), DB 이식성 정책 부재 |

종합 충족도: **약 60~70% (도메인 단일 화면 생성에는 충분, 빌드·운영 수준에는 미달)**

## 2. 보완 필요 사항 (코드생성 목적 기준 · 우선순위순)

| # | 구분 | 보완 내용 | 미보완 시 영향 |
|---|------|-----------|----------------|
| 1 | 요구사항 | 각 검증기준에 **입력→기대 출력/예외/메시지 구체값** 명시 | 단위테스트 `then` 자동 생성 불가(현재 TODO) |
| 2 | 프로그램설계 | **공통 모듈 표준** 정의: 글로벌 예외핸들러(@ControllerAdvice), 공통 응답/에러코드 체계, 인증·인가, 로깅 | 빌드/구동 불가, API 실패경로 미구현 |
| 3 | 화면설계 | API **실패 응답 규격**(에러코드↔HTTP↔메시지) 및 입력 검증규칙(형식·길이·범위) | 예외 흐름 코드 누락, 방어로직 빈약 |

| 6 | 화면레이아웃 | 컴포넌트 상태전이·이벤트·검증 메시지 위치의 **정밀 명세 또는 시안** | UI/UX가 추정으로 생성됨 |
| 7 | 데이터 매핑 | 테이블 컬럼 ↔ 화면항목 ↔ VO 필드 **완전 매핑표** | 매핑 일부 추정, 누락/불일치 위험 |
| 8 | 비기능 | 보안(개인정보 항목·다운로드 권한), 성능(대용량 엑셀 한도·동시성) 요구 | 비기능 코드/제약 미반영 |

## 3. 종합 결론

- **단일 도메인 화면의 골격 생성용으로는 입력 품질이 유효**(ID 추적성·4계층 매핑·테이블정의가 견고).
- 그러나 **(1) 검증기준 구체화, (2) 공통 아키텍처 표준 정의** 두 가지가 코드 자동생성 → 빌드·운영 도달의 **결정적 결손**이다. 이 둘만 보완해도 충족도가 크게 상승한다.
- 권고: 본 검토의 보완항목을 `aidd-templates/`의 요구사항정의서·프로그램설계서 템플릿에 **필수 입력 섹션으로 반영**하여, 다음 회차 입력 산출물 작성 시 누락을 구조적으로 차단할 것.

> 한계 명시: 본 평가는 입력 문서 원본을 직접 검수한 것이 아니라 생성 결과물 기반 역추적 판정이므로, 원본 제공 시 항목별 재검증이 필요하다.
